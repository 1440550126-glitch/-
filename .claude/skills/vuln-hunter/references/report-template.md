# 漏洞报告模板与评分

好报告的标准：**开发者读完就能复现、能理解、能修**。避免「可能存在潜在风险」式的空话——要么给出可复现证据，要么诚实标注需进一步验证。

## 严重级评分（CVSS 思路：影响 × 可利用性）

| 级别 | 判据 |
|---|---|
| **Critical** | 无需认证或普通权限即可达成：RCE、完整鉴权绕过、任意用户数据读写、资金损失、拿下服务器。利用简单、影响面大。 |
| **High** | 需要一定条件但影响重：越权访问敏感数据（IDOR）、SQL 注入（受限）、存储型 XSS 命中管理员、SSRF 打内网、支付逻辑绕过。 |
| **Medium** | 影响中等或利用需前置条件：反射型 XSS、CSRF、信息泄露（非关键）、弱口令策略、限流缺失致爆破。 |
| **Low** | 影响有限：轻微信息泄露、缺安全 header、用户枚举、点击劫持。 |
| **Info** | 非直接可利用，但降低整体安全性：最佳实践缺失、深度防御建议。 |

链条加成：多个 Low/Medium 若能串成完整攻击链，按**链条终态影响**定级，并在报告里讲清串联路径。

## 单条漏洞格式

```markdown
### [严重级] 简短标题（如：订单查询接口存在 IDOR，可越权读取任意用户订单）

- **位置**：`server/routes/order.js:42`（如涉多处，全部列出）
- **类别**：越权 / IDOR（CWE-639）
- **置信度**：已确认 / 需验证（说明还差什么证据）

**原理**
一句话讲清「哪个不可信输入，经由什么路径，到达什么危险操作，缺了什么防护」。

**复现步骤 / PoC**
1. 以用户 A 登录，拿到自己的订单 id=1001。
2. 发送 `curl -H "Cookie: token=<A的token>" https://host/api/order/1002`。
3. 返回了用户 B（id 归属 1002）的订单详情——服务端只按 id 查询，未校验归属。
（能给最小可复现请求/payload 就给；CTF 场景给完整利用链。）

**影响**
攻击者遍历 id 即可导出全站订单（含金额、收货信息……）。

**修复方案**
```js
// 错误：只按 id 查
const order = db.prepare('SELECT * FROM orders WHERE id = ?').get(id);
// 正确：绑定当前用户归属
const order = db.prepare('SELECT * FROM orders WHERE id = ? AND uid = ?').get(id, req.user.uid);
if (!order) return notFound();
```
给出正确代码，而不只是「应该做鉴权」。
```

## 整体报告结构

```markdown
# 安全审计报告 · <目标名> · <日期>

## 一、摘要
- 审计范围（哪些目录/组件）、方法、时间。
- **发现统计**：Critical N / High N / Medium N / Low N / Info N。
- 一句话总体风险结论。

## 二、严重级排序总表
| # | 级别 | 标题 | 位置 | 状态 |
|---|------|------|------|------|
| 1 | Critical | ... | file:line | 已确认 |
（让人一眼看到最该救火的。）

## 三、攻击链叙事
把散点串成故事：「攻击者从匿名开始，如何一步步（漏洞1→漏洞2→…）拿下 X」。
这比孤立列表更能说明真实风险，也帮助排优先级。

## 四、逐条漏洞详情
（按上面的单条格式，Critical 在前。）

## 五、加固建议（系统性）
超出单个漏洞的架构级建议：统一鉴权中间件、集中输入校验、参数化查询规范、
密钥管理、安全 header 基线、依赖治理、日志脱敏、生产配置检查清单。

## 六、未决 / 需进一步验证
无法当场确认但线索强的项，写清「需要什么才能证实」（如运行环境、真实数据、动态测试）。
```

## 报告纪律

- **不夸大**：没确认就别写「已确认可 RCE」。诚实标注置信度反而更可信。
- **不遗漏成片同类**：找到一个 IDOR，就把所有同模式接口都查一遍列进去。
- **可执行**：每条都要能让开发者据此复现与修复。
- **区分「漏洞」与「加固建议」**：真实可利用的进「漏洞」，最佳实践进「加固建议」，别混淆稀释重点。
